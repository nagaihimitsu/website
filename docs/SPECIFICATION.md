# 個人コレクションサイト｜企画書・実装仕様書

**文書版**：v1.0　　**作成日**：2026-10-18  
**用途**：個人ウェブサイトの企画確定・Codexへの実装引き継ぎ  
**サイト名**：未定（実装上の仮称は `Personal Atlas`。正式名称は後から変更できること）

> **最重要方針**：これは不特定多数のための記録アプリではない。所有者本人の「訪れた国」「訪れた都道府県」「登った日本百名山」「捕獲したポケモン」を、美しく見せるための**公開閲覧型の個人サイト**である。機能追加より、地図・図鑑・写真・タイポグラフィの完成度と、手編集の簡単さを優先する。

---

## 1. 企画の目的と完成像

### 1.1 目的
- 自分の実績を4つの一覧で管理し、誰でもブラウザから閲覧できるようにする。
- 「記録が増えると地図が塗られる／山のマーカーが変わる／図鑑が埋まる」視覚的な満足感を実現する。
- 各項目から訪問・登頂・捕獲の年月日と撮影写真を見られるようにする。
- 自分による更新は、テキストファイルと画像ファイルを変更するだけで済ませる。

### 1.2 機能よりも重視する体験
1. トップに4つのコレクションが端正に並び、進捗がひと目で分かる。
2. 世界・日本の地図は未訪問と訪問済みの違いが明確で、地図自体が美しい。
3. 百名山は100座すべてのマーカーが表示され、未登頂も「これからの場所」として見える。
4. ポケモンは全国図鑑順に整列し、通常色と色違いの2種類の達成状況が独立して分かる。
5. 項目を選ぶと、写真と日付が邪魔のないレイアウトで現れる。

### 1.3 対象・非対象
| 対象 | 非対象（初期版では実装しない） |
|---|---|
| 公開閲覧、所有者の手編集、4種類の実績、写真・日付 | ログイン、会員登録、管理画面、フォーム編集、データベース |
| 2D地図、世界の3D地球儀切替、百名山のマーカー、図鑑 | SNS、コメント、いいね、ランキング、通知、広告、収益化 |
| 読みやすいスマホ対応、最低限の検索・絞り込み | 旅行プラン、ナビ、現在地取得、GPS追跡、自動訪問判定 |
| 静的ホスティング、ビルド検証、写真最適化 | 大規模なCMS、クラウド同期、複数人編集、ゲーム要素 |

**言葉の定義**：「閲覧者」はサイトを訪れる人。「更新者」はTXTと写真を変更する所有者本人のみ。ブラウザからの編集機能は作らない。

## 2. 確定要件・設計上の判断

| ID | 項目 | 確定仕様 | 優先 |
|---|---|---|---|
| R01 | 公開 | インターネット上で誰でも閲覧可能な個人サイト | MUST |
| R02 | 編集 | ローカルまたはGitリポジトリでTXT・写真を編集して更新 | MUST |
| R03 | 保存形式 | 実績・詳細記録はUTF-8の `.txt`。JSONは地図等の読み取り専用マスターに限る | MUST |
| R04 | 国 | 訪問した国を色付けする世界地図と一覧、訪問数 | MUST |
| R05 | 都道府県 | 47都道府県すべての地図と一覧、訪問数 | MUST |
| R06 | 百名山 | 日本百名山100座の位置に登頂済み・未登頂の色違いマーカー | MUST |
| R07 | ポケモン | 全国図鑑の全基本種、通常色・色違いを別々に登録・集計 | MUST |
| R08 | 日付 | 任意。`YYYY`／`YYYY-MM`／`YYYY-MM-DD`／空欄を許容 | MUST |
| R09 | 写真 | 任意。項目あたり0枚以上。1回の記録に複数写真可 | MUST |
| R10 | 複数回 | 同じ国・県・山・ポケモンへ複数の年月日・写真記録を紐づけ可 | MUST |
| R11 | 3D | 世界地図で「2D地図／3D地球儀」を切替できる | MUST |
| R12 | 拡張性 | ポケモンのリージョン・姿違い対応を後から加えられるID設計 | SHOULD |
| R13 | デザイン | ダーク基調、ミニマル、写真と地図を主役にした統一UI | MUST |
| R14 | データ検証 | 不明な名前・重複・誤日付・欠損画像等をビルド前に確認 | MUST |
| R15 | 公開形式 | 静的サイト。閲覧時のサーバーAPI・DB・ログインは不要 | MUST |

**優先度**：MUST＝初期完成条件、SHOULD＝実装が単純なら初期対応／構造として確保、MAY＝将来構想。

### 2.1 あえて追加しないもの
「誰でも使いやすい汎用アプリ」を目指さない。初回オンボーディング、設定ページ、管理者UI、複雑なプロフィール、ゲーミフィケーション、多機能な旅行記エディタは不要。

### 2.2 まだ決める必要のないもの
独自ドメイン、サイト名、本人のプロフィール表示、ポケモン画像の最終採用元は後から変更できるようにする。これらが未決定でも開発を止めない。

## 3. サイトのページ構成・表示仕様

### 3.1 ページ一覧
| URL例（静的公開を考慮したハッシュルート） | ページ | 主な要素 |
|---|---|---|
| `/#/` | ホーム | 4コレクションの大きなカード／件数／導線 |
| `/#/world` | 訪問した国 | 世界地図、2D/3D切替、国一覧、訪問国数 |
| `/#/japan` | 訪問した都道府県 | 日本47都道府県地図、一覧、訪問数 |
| `/#/mountains` | 登頂した日本百名山 | 日本地図＋100マーカー、山一覧、登頂数 |
| `/#/pokemon` | 捕獲したポケモン | 全国図鑑グリッド、通常色／色違いの表示・集計 |

ページを増やさず、国・県・山・ポケモンの個別詳細は**共通の詳細パネル（PC：サイドパネル、スマホ：下から開くパネル）**で表示する。別ページへ遷移させない。

### 3.2 ホーム
- ページ冒頭に短いタイトルと控えめな説明文のみ。
- 4つの主カードを2×2（広い画面）／縦並び（スマホ）に表示。
- 各カードには「タイトル／大きな達成数／小さなプレビュー／開く導線」を配置。
- 進捗表記は「都道府県 12/47」「百名山 20/100」「ポケモン 捕獲123種／通常色○／色違い○」のような集計から自動生成。**数値をHTMLに手書きしない**。
- 国の達成率は「対象とする国・地域の分母」の定義に依存するため、初期表示は原則「訪問○か国」。必要なら分母定義を定めた上で割合も表示。曖昧な195／249等を固定で書かない。

### 3.3 訪問した国
- ベクターデータから2D世界地図を表示。訪問済みの国をアクセント色、未訪問を低彩度色で塗り分ける。
- `2D / 3D` の切替を設ける。**同じ訪問IDの集合を2D/3D双方へ流し込む**。表示モードごとのデータ二重管理は禁止。
- 3Dではドラッグで地球儀を回転、スクロール・ピンチで拡大縮小。訪問済み地域をハイライト。選択した国は詳細パネルへ。
- 国が小さくタップしにくい場合に備え、**国名一覧／検索を常に代替手段として用意**する。
- 3D初期位置・回転速度は控えめ。自動回転は原則オフ。
- WebGL不可／性能不足時は2Dへ安全に切り替え、閲覧機能を失わせない。
- 島・飛地・境界が多い国も同一の国IDへ紐づける。地図データで割り当て不能な国・地域は一覧から閲覧可能とし、黙って誤った国を着色しない。

### 3.4 訪問した都道府県
- **47都道府県すべて**を表示し、訪問済みのみアクセント色にする。
- 北海道と沖縄などをスマホで読みやすくするため、沖縄・離島は別枠表示（インセット）も可。ただし地域を欠落させない。
- 地図クリックと県名一覧のどちらからも詳細を開ける。
- 件数はユニークな都道府県数で集計し、`/47` を表示。
- 山に登ったという事実だけで訪問県を自動で追加しない。各TXTを独立した記録として扱う。

### 3.5 登頂した日本百名山
- 日本地図上に**100座すべてのピン**を表示。未登頂も必ず表示。
- 登頂済み＝明るいアクセント色＋輪郭、未登頂＝くすんだ色＋輪郭。状態が色以外でも識別可能になるようラベルや凡例を添える。
- 密集域は地図の拡大やリストの連動で選択可能にする（100座が重なっても消失させない）。
- `登頂済み 20 / 100` のような件数を自動集計する。
- 「深田久弥『日本百名山』の100座」という固定のマスター一覧を採用する。別の百名山・二百名山・アルプスの人気山を混ぜない。
- 例：**「穂高岳」**を1座としてカウントし、`奥穂高岳` などの通称・主峰名を同じマスターIDへ正規化できるようにする。**「燕岳」は日本百名山ではない**ため、100座の一覧へ追加してはならない。
- 複数山頂がある山のピン位置は「代表山頂」を1つ採用し、その根拠をマスターに記録。緯度経度を推測で作らない。
- 立体山岳地形（3D DEM）は初版には含めず、将来の拡張とする。初版の3D要件は世界の地球儀切替で満たす。

### 3.6 捕獲したポケモン
- **全国図鑑の基本種（species）**が図鑑番号順に欠けなく並ぶ。図鑑対象総数は採用したマスタースナップショットから取得し、数字をコードへ直書きしない。
- **通常色と色違いを独立した真偽値として管理**する。4状態を正しく表現：未捕獲／通常色のみ／色違いのみ／両方。
- 「捕獲済みの種類数」は通常色と色違いの和集合（重複しない種類数）。さらに通常色の数・色違いの数・両方の数を別表示する。
- 番号・日本語名の表示、名前・番号検索、捕獲済み／未捕獲の切替を実装。世代フィルタは余力があれば対応。
- 各カードは数字・名称が主役。通常色／色違いの状態が小さく明確に伝わる2つのインジケータを持つ。
- ポケモンの公式画像・スプライトは**権利確認を行った場合のみ**使用する。確認できない場合はテキスト主体の高品質な図鑑デザインで先に完成させ、画像なしでも破綻させない。
- 初版ではリージョンフォーム・姿違い・メガ進化を別カウントしない。ただし内部キーは`speciesId`と将来の`formId`を分離しやすい構造とする。

### 3.7 共通詳細パネルと写真
- 地図・図鑑で項目を選ぶと、**名前／達成状態／関連する日付・写真**を表示。
- 1項目に複数の記録があれば日付順（原則新しい順、日付不明は末尾）で並ぶ。
- 年しかない記録は年のみ、年月は年月のみ。**存在しない月日を補完・表示しない**。
- 画像は0枚でも成立し、画像があるときは1枚目を代表にし、複数枚なら左右操作／サムネイルで切替。画像比率を維持し、不必要にトリミングしない。
- 画像クリックで拡大。背景クリック・Escape・閉じるボタンで戻れる。
- 日付なし・写真なしは大げさな空欄UIを出さず、項目名と状態だけを整然と表示。

## 4. デザインシステム（最優先）

### 4.1 全体方向
**コンセプト**：`Quiet Atlas / Personal Archive`（仮のデザインコンセプト。サイト名称ではない）  
**印象**：静けさ／精密さ／探検／記録／写真展示。旅行アプリの賑やかな広告画面や、ゲーム的な派手なUIにはしない。

### 4.2 色の初期案（微調整可）
| 用途 | カラー案 | 運用 |
|---|---|---|
| 背景 | `#0B1118` | ほぼ黒のネイビー |
| パネル | `#14202B` | 背景より一段明るく |
| 線・境界 | `#263845` | 細い輪郭 |
| 本文 | `#EEF3F5` | 高コントラスト |
| 補助文字 | `#A5B4BF` | 落ち着いた灰青 |
| 訪問済み国 | `#6CD8BE` | 青緑系 |
| 訪問済み都道府県 | `#79A9E5` | 青系 |
| 登頂済み | `#E0BD81` | 上品な琥珀 |
| ポケモンの通常色／色違い | `#80C9C1`／`#C4A4E9` | 2状態を区別 |
| 未達成 | `#41515D` | 明暗を抑える |

- 色が違っても明るさの階層・文字の組み方・パネルの余白は共通。
- ネオン発光・グラデーション・シャドウはアクセントに留める。読みにくい半透明文字は禁止。
- フォントは日本語に読みやすいシステムフォントを利用。外部フォント読み込みは必須にしない。

### 4.3 レイアウト
- PC：最大コンテンツ幅およそ1200〜1440px、余白を広く、ホームは2列カード。地図＋右詳細パネル。
- スマホ：余計なメニューを増やさず、上部にページ名、下部または上部に4セクションの切替。地図は広く、詳細はボトムシート。
- カード角丸は控えめ、余白は24〜32pxを基準。過密な表・バッジの乱用は避ける。
- 最低限の動き：項目選択、色の遷移、パネルの出入り。`prefers-reduced-motion`に対応。
- モバイル操作領域は44px程度を目安に確保。国の極小ポリゴンはリスト選択でカバー。

### 4.4 写真の扱い
- 原則「自分で撮影した写真」を配置し、強いフィルタ・過度な色補正をしない。
- タイル状に大量表示するのではなく、詳細パネルで余白と日付を活かして見せる。
- 未設定ならダミーの写真を勝手に差し込まない。色面・図形・タイポグラフィで成立させる。
- 公開写真はWeb用にリサイズ・圧縮し、EXIF位置情報等を削除する。

## 5. 編集用TXTの仕様（必須）

### 5.1 原則
- 更新者が普段編集するのは**実績TXT 5個と、必要に応じて詳細TXT 4個**のみ。画像は所定フォルダへ配置する。
- 保存はUTF-8。BOMあり・なし、LF／CRLF、空行、先頭・末尾の空白に対応。
- 行頭 `#` はコメントとして無視。全角空白は名前の前後だけ除去。項目名の内部を勝手に変形しない。
- 実績TXTは**1行1項目を推奨**、`日本,アメリカ,イギリス` のような1行カンマ区切りも許す。外側に `{...}` を付けた場合も許容できるとさらに親切（この表記は補助対応でよい）。
- 画面側は、実績TXTだけを編集すると即座にカウント・色・一覧が変わる仕組みとする。
- TXTに入力するのは日本語名または図鑑番号などの簡単な値。地図座標・ISOコード・集計値を所有者に手入力させない。
- TXTから直接HTMLを注入しない。入力はテキストとして安全に表示する。

### 5.2 実績TXT（5ファイル）

**`public/data/訪問した国.txt`**
```txt
# 1行1件。カンマ区切りも可
日本
アメリカ
イギリス
```

**`public/data/訪問した都道府県.txt`**
```txt
東京都
埼玉県
長野県
```

**`public/data/登頂した百名山.txt`**
```txt
富士山
穂高岳
槍ヶ岳
```

**`public/data/ポケモン_通常色.txt`**
```txt
# 図鑑番号でも日本語名でも入力可
1
25
150
```

**`public/data/ポケモン_色違い.txt`**
```txt
25
150
```

**内部正規化**：同義語・名称ゆれは読み込み側のマスターに集約する。例：`アメリカ`と`アメリカ合衆国`→同じ国ID、`東京`と`東京都`→同じ県ID、`奥穂高岳`と`穂高岳`→同じ百名山ID、`025`と`ピカチュウ`→同じ図鑑番号。重複カウントは禁止。

### 5.3 日付・写真の詳細TXT（4ファイル）
実績TXTを複雑にしないため、**詳細は別ファイルへ追記**する。どの詳細TXTも日付・写真は空欄でよい。

**`public/data/記録_国.txt`**
```txt
# 国名|年月日（任意）|写真相対パスをカンマ区切り（任意）
日本|2024-05|countries/japan/01.webp,countries/japan/02.webp
日本|2025-04-02|countries/japan/03.webp
イギリス|2022|
```

**`public/data/記録_都道府県.txt`**
```txt
# 都道府県|年月日|写真（0枚以上）
長野県|2025-10-12|prefectures/nagano/01.webp
東京都||
```

**`public/data/記録_百名山.txt`**
```txt
# 百名山名|登頂年月日|写真（0枚以上）
穂高岳|2025-09|mountains/hotaka/01.webp,mountains/hotaka/02.webp
富士山|2024-07-21|
```

**`public/data/記録_ポケモン.txt`**
```txt
# 図鑑番号または名称|normal または shiny|年月日|写真（0枚以上）
25|normal|2024|pokemon/025_normal.webp
25|shiny|2025-08-01|pokemon/025_shiny.webp
```

**詳細行の意味**：1行＝1回の訪問・登頂・捕獲に相当する記録。複数回なら同じ項目名で複数行。ポケモンは`normal`／`shiny`を明示。日付は `2024`、`2024-05`、`2024-05-12`、空欄のみ。`2024-02-30`のような不正な日付を受け付けない。

### 5.4 画像パスと代表画像
- パスは `public/photos/` からの相対パス。例：`countries/japan/01.webp` は `public/photos/countries/japan/01.webp` を指す。
- 先頭 `/`、`..`、外部URLは禁止。ファイル名には `|` と `,` を使わない。
- 1レコードの写真は左から記述順。項目の代表画像は**最新の写真付き記録の最初の画像**を自動採用（詳細記録がなければ代表画像なし）。
- 画像は JPG／PNG／WebP／AVIF を許容。公開用にはWebPを推奨。SVGは写真として受け付けない。
- 元写真を自動で公開フォルダへ入れず、所有者が公開してよいと判断したファイルのみ配置。

### 5.5 正規化・整合性エラー
| ケース | 処理方針 |
|---|---|
| 同じ項目が実績TXTに2回 | 重複は1件として扱い、バリデーターで警告 |
| 未知の国・県・山・ポケモン | ビルド前検証でエラー。ファイル名・行番号・候補を出す |
| `燕岳` が百名山TXTにある | 百名山外としてエラー。勝手に101座へ増やさない |
| 詳細TXTにある項目が実績TXTにない | 不整合エラー。詳細だけで訪問・捕獲済みに変更しない |
| 不正な日付（例：2025-13、2024-02-30） | エラー。勝手な補正はしない |
| 画像ファイルが存在しない／危険なパス | エラー。壊れた画像を静かに表示しない |
| 日付・写真が空欄 | 正常。未入力として扱う |
| データが0件 | 正常。空の地図・図鑑とゼロ件表示が成立 |
| 詳細記録が同日複数行 | 正常。複数回の記録として保持 |

### 5.6 内部マスター（所有者は普段編集しない）
実績TXTから地図や図鑑に変換するため、別途アプリ側の**読み取り専用マスター**を持つ。

- **国マスター**：固定ID（原則ISO 3166-1 alpha-3）、日本語表示名、別名、地図のポリゴンIDへの対応、カウント対象設定。
- **都道府県マスター**：JIS系の2桁都道府県コード、47都道府県の正式名称と別名、地図データID。
- **百名山マスター**：ちょうど100件。固定ID、正式名称、別名、代表山頂の緯度経度、その採用根拠。代表座標は信頼できる地図等で要検証。
- **ポケモンマスター**：全国図鑑番号、基本種ID、日本語名、英語名（内部参照用）、世代など。出典と取得時点を固定したスナップショットをビルドに同梱する。

**大切な境界**：国境ポリゴン、ポケモン種族一覧、百名山位置などは「TXTに書く利用者データ」ではなく「コードが読む辞書データ」。毎回の閲覧時に外部APIへ問い合わせない。

## 6. 国・山・ポケモンの対象範囲

### 6.1 国と「訪問○か国」の考え方
国の数え方には、国連加盟国と非加盟の国・地域、海外領土、政治的に扱いが異なる地域がある。よって、アプリ内で「全世界195か国」などの分母を根拠なく固定しない。

- 初版は選定した**国・地域マスターにある項目のユニーク訪問数**を表示。
- 進捗率を表示する場合は `countTowardsTotal` の対象一覧・基準日を明記し、分子も同じ対象にそろえる。
- 訪問済TXTには日本語の短い名称を記入できる。名前と地図の対応付けはマスターが責任を持つ。
- ポリゴンが存在しない・一部地域だけが描ける場合は名前一覧を正とし、無理に誤着色しない。

### 6.2 日本百名山の粒度
- 単位は「深田久弥の日本百名山に収載された山」1件。
- 代表峰名の表記ゆれを整理し、例えば穂高岳の奥穂高岳登頂は同じ1件へ正規化する。
- すべての名称・代表座標を照合し、**100件、ID重複0件、位置欠損0件**を受入条件とする。
- 気軽なサンプルリストに含まれがちな燕岳などを百名山として混入させない。

### 6.3 ポケモンの粒度
- 1全国図鑑番号＝1基本種。通常色と色違いは**別の収集フラグ**だが、種族数は1のまま。
- 色違いしか登録されていなくても「捕獲済み種類数」には含む。通常色を自動で捕獲扱いにしない。
- 将来フォームを追加した場合に備え、将来の記録IDは `speciesId + variant(normal/shiny) + optional formId` として拡張可能にする。
- フォーム解放時も、既存の通常色・色違いTXTの意味と記録を保持する。

## 7. 想定技術構成

| 領域 | 第一候補 | 選定理由・制約 |
|---|---|---|
| フロントエンド | React + TypeScript + Vite | 静的出力、画面部品の再利用、Codex実装の保守性 |
| UI | CSS Modulesまたは素のCSS／CSS変数 | デザイン統制。重いUIコンポーネント集は使わない |
| 2D地図 | SVG + d3-geo + TopoJSON/GeoJSON | 軽量で配色・クリック・画面調整を自由にできる |
| 3D地球儀 | `react-globe.gl`（必要時のみ動的import） | GeoJSONポリゴンの色分け・操作。WebGL非対応は2Dへ |
| 世界地図データ | Natural Earth | 公共利用しやすいデータ。バージョン・地図IDを固定 |
| 日本の都道府県形状 | 権利を確認したTopoJSON／GeoJSON（例：`jpn-atlas`） | 47県を表示。出典・ライセンス表記を残す |
| 百名山座標 | 手検証した100座マスター | 代表峰を明示。誤座標を防止 |
| ポケモン基礎データ | PokéAPIのspecies情報などから**開発時に生成** | 日本語名・図鑑番号をスナップショット化。閲覧時API通信不要 |
| 編集用データ | UTF-8 TXT | 所有者がテキスト編集できる |
| 写真 | `public/photos/` | サイト内の静的画像。EXIF除去・画像最適化 |
| 公開 | GitHub Pages等の静的ホスティング | サーバー・DB・ログインが不要。公開先は変更可能 |
| テスト | Vitest、最低限のPlaywright E2E | 日付・重複・4画面・地図操作・図鑑集計を検証 |

- 原則として**地図用のAPIキー、有料地図API、バックエンド、DB、外部認証は使わない**。
- 地図・ポケモンのマスターはリポジトリへ同梱し、閲覧者の回線で外部ソースから取得する必要をなくす。
- 静的ホスティングで再読み込みしても404にならないようハッシュルーティングを推奨。
- `import.meta.env.BASE_URL` などを用い、GitHub Pagesの `/<repo>/` 配下でもTXTや画像のURLが壊れないようにする。

## 9. データ読み込みと画面更新の設計

1. ブラウザ起動時、静的公開されたTXTを読み込む。
2. パーサーが空行・コメント・カンマ区切りを処理し、各実績を正規化されたIDへ変換する。
3. 集計ロジックが訪問数・登頂数・ポケモン各状態数を計算する。
4. 地図・図鑑はID集合を参照して着色する。
5. 詳細パネルは同じIDに紐づく年月日・写真を表示する。
6. 運用時はTXTや写真を編集してリポジトリに反映し、再公開すると表示が更新される。

**片方向のデータフロー**：`TXT → パーサー → 正規化された記録 → 件数／地図／図鑑／詳細`。

実績TXTだけを編集した場合、詳細TXTを作る必要はない。例えば国ファイルを`日本,アメリカ,イギリス`に更新すると、**3か国表示と3か国の着色が自動で成立**する。

## 10. 性能・スマホ・品質

### 10.1 性能
- 2Dと4ページの基本閲覧にWebGLを必須にしない。
- 3D実装は該当ページ／モードで初めて遅延読み込みする。3Dが起動しない場合も2Dが残る。
- ポケモン大量カードは表示範囲に応じて描画・画像を遅延読み込みする。全カードの大画像を一括取得しない。
- 地図はSVG/TopoJSONを軽量化し、スマホでページ操作が重くならないようにする。
- 画像は適切なサイズに縮小してWebP等で公開、`loading=lazy` を基本とする。

### 10.2 UI・アクセシビリティ
- 360〜430px程度の狭いスマホでも横スクロールを発生させない。
- PC・スマホの両方で地図→詳細パネルが正常に動く。
- キーボード操作・閉じるボタン・フォーカス移動を維持。
- 状態を色だけに依存させず、凡例・テキスト・マークでも区別。
- 写真に代替テキスト（デフォルトは項目名）を設定し、主要な数値はテキストで示す。

### 10.3 公開時の注意
- TXTも写真も**誰でも取得可能**。閲覧者に見せたくない情報は置かない。
- 公開画像に位置情報・撮影機材情報・個人情報等が残らないようEXIF削除を推奨／ツール化する。
- 顔・住所・予約情報などが写る画像は公開前に確認する。
- Git履歴へ一度登録した画像は、後に消しても履歴に残り得る。原本は別管理する。
- ビルドに秘密鍵、トークン、個人的な生データを含めない。

### Phase 0：土台とデザインの試作

- 47県・100山・ポケモン全国図鑑のマスターを準備。

**合格**：TXT変更で件数が自動更新され、無効データはエラー位置が分かる。100山・47県の件数が保証される。

### Phase 2：地図
- 2D世界地図、2D日本地図、百名山100マーカーを実装。

**合格**：訪問・登頂TXTを変えると対応する地図色／マーカーが変わる。100座を一覧から確実に探して開ける。

### Phase 3：ポケモン図鑑
- 基本種の全件グリッド、検索、4状態表示、件数集計、詳細パネルを実装。

- 複数回記録、任意日付、複数写真、拡大、モバイル詳細パネルを実装。

- 各ページの余白、文字、地図の細部、遷移を調整。

**合格**：TXTと写真の編集だけで更新でき、`npm run test`、`npm run validate:data`、`npm run build`を通過し、PC／スマホで問題なく閲覧できる。

## 14. 最終完成の定義（Definition of Done）

以下を全て満たすこと。

1. 4コレクションが美しい統一UIで閲覧できる。
2. 実績TXT 5つを編集すると、件数・達成状態・地図・図鑑が自動更新される。
3. 詳細TXT 4つと画像を配置すると、0件〜複数件の年月日・写真が正しく表示される。
4. 都道府県47／百名山100／採用時点の全国図鑑基本種全件をマスターとして表示し、未達成も一覧から消えない。
5. 国は2D世界地図と3D地球儀の切替が実際に動く。非対応環境は2Dで閲覧できる。
6. ポケモンの通常色と色違いが独立し、4状態と各件数が正しい。
7. PCとスマホの両方で読みやすく、操作しやすい。
8. DB・ログイン・ブラウザ編集・外部APIキーに依存しない静的サイトになっている。
9. テスト・データ検証・本番ビルドが成功する。
10. READMEに、TXT1行追加・写真追加・公開更新の手順と外部データの出典が書いてある。

**最終判断基準**：新機能の多さではなく、「自分の実績を美しく眺める」という目的を達成できているか。曖昧な要件を勝手に一般向けのサービスへ広げないこと。
